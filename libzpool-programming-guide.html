libzpool Programming Guide

Patterns, pitfalls, and crash-to-fix recipes for userspace ZFS code

This document records the hard-won lessons from building and debugging the rebase_test harness against libzpool. Every section corresponds to a real crash we hit and diagnosed. The canonical upstream reference is cmd/ztest.c in the OpenZFS tree.

1. FTAG is __func__

FTAG is defined in include/sys/zfs_refcount.h as:

#define FTAG ((char *)(uintptr_t)__func__)

Every function that uses FTAG gets a different pointer value. This matters because dmu_objset_own() stores the tag as the dataset owner, and dmu_objset_disown() checks it with pointer equality.

Crash signature. VERIFY3P(ds->ds_owner, ==, tag) failed in dsl_dataset_disown(). The two hex values in the assertion are the string addresses of two different function names.

The bug

A helper function calls dmu_objset_own(..., FTAG, &os), which records the tag as the helper's __func__ string. The caller later calls dmu_objset_disown(os, B_FALSE, FTAG), but its FTAG points to a different __func__ string.

The fix

Pass the tag as a parameter through any helper that calls dmu_objset_own. This is exactly what ztest_dmu_objset_own() does in ztest.c:

/* Helper accepts tag from caller */
static int
open_dataset(const char *dsname, objset_t **osp,
    const void *tag)
{
    err = dmu_objset_own(dsname, DMU_OST_ZFS,
        B_FALSE, B_FALSE, tag, osp);
    ...
}

/* Caller uses same FTAG for both */
err = open_dataset(name, &os, FTAG);
...
dmu_objset_disown(os, B_FALSE, FTAG);

2. SA handle lifecycle

The system attribute (SA) subsystem has two ways to get a handle. Only one of them adds a buffer hold. sa_handle_destroy() always releases one. Getting this wrong causes a refcount double-release.

Crash signature. VERIFY3S(count, >=, 0) failed (-1 >= 0x0) in zfs_refcount_remove_many(), typically on the dp_sync_taskq thread during dbuf_sync_bonus.

How the functions work

Function Adds buffer hold?
sa_handle_get(os, obj, NULL, SA_HDL_SHARED, &hdl) Yes — calls dmu_bonus_hold() internally
sa_handle_get_from_db(os, db, NULL, SA_HDL_SHARED, &hdl) No — wraps an existing buffer, adds no hold
sa_handle_destroy(hdl) Always releases — calls dmu_buf_rele(hdl->sa_bonus, NULL)

Correct pattern

sa_handle_t *hdl;
VERIFY0(sa_handle_get(os, obj, NULL, SA_HDL_SHARED, &hdl));
/* ... use hdl ... */
sa_handle_destroy(hdl);

This is balanced: one hold from sa_handle_get, one release from sa_handle_destroy.

Wrong pattern

dmu_buf_t *db;
sa_handle_t *hdl;
VERIFY0(sa_buf_hold(os, obj, FTAG, &db));        /* hold #1 */
VERIFY0(sa_handle_get_from_db(os, db, NULL,
    SA_HDL_SHARED, &hdl));                        /* no hold */
/* ... use hdl ... */
sa_handle_destroy(hdl);                           /* release #1 */
sa_buf_rele(db, FTAG);                            /* release #2 -- BOOM */

Two releases against one hold. The refcount goes to −1 and triggers an assertion in the sync task that later touches the buffer.

3. Dataset opening: own vs. hold

There are two ways to open a dataset. They have different locking behavior that matters when you need to run transactions.

Function pair Config lock behavior
dmu_objset_hold / dmu_objset_rele Keeps the DSL pool config lock as a reader for the duration
dmu_objset_own / dmu_objset_disown Acquires ownership, releases the config lock after setup

Crash signature. ((flags & DMU_TX_WAIT)) implies (!dsl_pool_config_held(tx->tx_pool)) assertion failure in dmu_tx_assign().

The rule

dmu_tx_assign(tx, DMU_TX_WAIT) asserts that the config lock is not held, because it may need to wait for sync and re-acquire it. If you opened the dataset with dmu_objset_hold, the lock is still held and the assertion fires.

  • Use own/disown when the code needs to create and commit transactions.
  • Use hold/rele for read-only access (lookups, comparisons, iteration).

4. Transaction holds

Before calling dmu_tx_assign(), every block that will be dirtied must have a corresponding dmu_tx_hold_* call. Missing a hold causes a panic at dirty time, not at hold time, which makes the error message point at the wrong place.

Crash signature. PANIC: dirtying dbuf obj=N lvl=0 blkid=0 but not tx_held — the object number tells you which hold is missing.

Hold recipes by operation

Operation Required holds
Create a regular file (dmu_object_alloc) dmu_tx_hold_sa_create(tx, bonuslen)
dmu_tx_hold_write(tx, DMU_NEW_OBJECT, 0, len) (if writing data)
dmu_tx_hold_zap(tx, dir_obj, B_TRUE, name) (parent dir entry)
Create a directory (zap_create_norm) dmu_tx_hold_zap(tx, DMU_NEW_OBJECT, B_TRUE, NULL) (new ZAP data block)
dmu_tx_hold_sa_create(tx, bonuslen) (bonus buffer)
dmu_tx_hold_zap(tx, parent_obj, B_TRUE, name) (parent dir entry)
Edit file data dmu_tx_hold_write(tx, obj, offset, len)
Modify SA attributes dmu_tx_hold_bonus(tx, obj)
Add/remove ZAP entry dmu_tx_hold_zap(tx, dir_obj, adding, name)

Why directories need an extra hold. zap_create_norm() calls mzap_create_impl() which initializes the micro-ZAP header in data block 0. Without dmu_tx_hold_zap(tx, DMU_NEW_OBJECT, ...), the data block has no space reservation and the dirty triggers a panic. Regular files created with dmu_object_alloc() don't initialize a data block at creation time, so they don't need this hold.

5. Sync task callbacks

The callback passed to dmu_objset_create() (e.g., zpl_create_cb) runs inside a sync task. The transaction tx passed to the callback has broader permissions than a normal transaction:

  • Explicit dmu_tx_hold_* calls are not needed for objects created within the callback.
  • The callback runs in the syncer context after the objset is already created on disk.
  • You can freely call zap_create_claim(), zap_create(), zap_add(), sa_setup(), sa_replace_all_by_template(), etc.

This is how our zpl_create_cb creates the MASTER_NODE, SA registration, delete queue, and root directory all in one callback without any hold declarations.

6. Quick reference: common hold/release pairs

Acquire Release Notes
dmu_objset_own() dmu_objset_disown() Same tag required (see section 1)
dmu_objset_hold() dmu_objset_rele() Read-only; holds config lock
sa_handle_get() sa_handle_destroy() Balanced pair (see section 2)
spa_open() spa_close() Same tag; fine with FTAG in same function
dsl_pool_hold() dsl_pool_rele() Same tag
dsl_dataset_hold() dsl_dataset_rele() Same tag
dmu_tx_create() dmu_tx_commit() or dmu_tx_abort() Abort on dmu_tx_assign failure

7. Debugging tips

  • Build with -O0 -g so GDB can show local variables and you get accurate line numbers in assertions.
  • Always run as root (sudo ./rebase_test) — kernel_init() opens /dev/zfs.
  • Clean up stale pools. Call spa_destroy() and unlink() at the start of your test scaffold, not just at the end. A prior crash leaves the pool imported.
  • Read the assertion message carefully. ZFS VERIFY/PANIC messages print the exact expression and values. The object number in a "not tx_held" panic tells you which hold is missing. The thread name tells you if it crashed in the sync task vs. the calling thread.
  • clangd diagnostics on macOS are noise. Kernel headers don't resolve outside FreeBSD/Linux. The build uses -include flags that clangd doesn't see.

Reference code. cmd/ztest.c in the OpenZFS tree is the canonical example of userspace libzpool programming. When in doubt about a pattern, check how ztest does it.
